## 1. Executive summary

The engine core is real and defensively well-built: text rules, NSFW image (onnx),
whisper audio, ffmpeg video detect+remediate, fail-closed-on-uncovered policy,
accounts (PBKDF2, throttled, scoped), ChildControl (monotonic, guardian-scoped,
persisted), the review/alert relay, the cluster lease queue, and the explicit-proxy
binary are implemented and tested, and the planning docs are unusually honest about
most seams. The crown-jewel invariants verify clean in code: **CSAM is never stored,
previewed, or served** (enforced at the lowest store layer + UI + server approve
path), evidence is redacted with belt-and-braces asserts, the per-install CA is never
shared or baked in, upstream TLS *is* validated, and no secrets or model artifacts
are in the tree.

The audit found **two compound critical problems**:

1. **The production transport is plaintext.** mTLS is written in code
   (`service::run` wires `ServerTlsConfig`) but never provisioned: the London EC2
   serves gRPC unencrypted on a security group whose default is open to
   `0.0.0.0/0`, and the parent app's default UK endpoint is `http://`. Guardian
   passwords, 12-hour bearer tokens, and pair codes cross the internet in clear.
   This contradicts the threat model's central "mutual TLS, no plaintext fallback"
   claim. **This is live on master today — it predates PR #101.**

2. **The Android child device's protection loop is hollow, and every channel that
   would reveal that is also broken** — four undocumented gaps that compound:
   - `run_android_data_path` starts the proxy + packet pump but **nothing consumes
     the captured flows** — no pipeline, no classification, no policy, no content
     alerts. Decrypted scorable media is blanket-dropped by the 5s fail-closed
     timeout instead of scored; everything else forwards unclassified — while the
     foreground notification says "Filtering content and watching for grooming
     signals."
   - The per-session in-memory CA is never trusted by Android, so nearly all HTTPS
     strikes out → pinned → **fail-open tunnel-through**, justified by an OCR route
     that does not exist (`bulwark-agent` has no capture loop and is not in the
     client dep tree).
   - The one real detector (accessibility, 6 hardcoded apps) and ALL tamper events
     terminate in a **local, dismissible notification on the child's own phone** —
     `TamperReporter.kt` claims cluster relay; the queue is a local loopback, and
     Android sends no heartbeats so the server's missed-heartbeat sweep can never
     notice the device going dark.
   - The child dashboard renders "protection active" from stored **consent**, not
     the live service (`vpnRunning = vpnConsented`).

   Net effect: parent console shows "Applied ✓" (real) and a Coverage tab hardcoded
   to "Filtered" (fake) while actual Android protection ≈ QUIC blocked + DNS
   forwarded + 6-app accessibility text checks with local-only alerts.

Everything else is either documented design seams (supervision stubs, OCR agent,
desktop transparent VPN fail-closed, gossip placeholder) or smaller fixable items
listed below.

## 5. Plan-vs-reality: status corrections needed

Verified matrix of 40 capabilities: 19 ✅ working, 8 🟠 partial, 5 🧪
implemented-but-unvalidated (device/credentials), 4 ❌ missing, 1 📄 doc-only
(SMS/calls — honestly labeled). PLAN.md §6 + production-readiness.md are the
trustworthy surfaces. Docs needing correction:

1. **README.md** — "Windows VPN works today" is false (fail-closed by design);
   "email + push" presents push as live (feature-gated, needs FCM).
2. **docs/design/runtime-modes.md** — stalest doc: still names tun2proxy (removed,
   GPL) as the Windows/Linux/macOS mechanism; `setup(true)` route claim.
3. **docs/running.md** — "not compile-verified" banner (two waves stale) and
   "models fail open" (inverted to fail-closed long ago).
4. **docs/deployment.md** §4/§5/§11/§13 — fail-open wording; "FetchSegment playback
   is remaining wiring" (it shipped); Android tamper-relay guarantee overstated.
5. **docs/design/on-device-scanning.md** appendix — "clip-fetch not implemented"
   (shipped: `Review.FetchSegment` + parent playback).
6. **docs/design/app-pairing-and-regions.md** — claims Dioxus 0.6 pin (apps are on
   0.8.0-alpha.0).
7. **docs/design/apps.md** — Android "built (transparent)" missing the
   device-validation caveat; Apple shell "to build" though a real
   NEFilterDataProvider skeleton exists in `platform/apple/`.
8. Shipped-but-undocumented win: remote video review (FetchSegment → parent `<video>`
   playback) is fully working.

## 6. Prioritized fix roadmap

**P0 — security/honesty, before or immediately after the next deploy**
1. Provision TLS/mTLS for the production transport (cert+key+client-CA through
   `BULWARK_TLS_*` → main.rs → deploy.yml → user_data); switch UK endpoint to
   `https://`; parent app refuses plaintext for login; close SG defaults. (C1)
2. Hash session tokens at rest (or stop persisting them); `chmod 700` the state
   dir. (High)
3. Honesty hot-fixes (hours, not days): delete/derive the parent `CoverageMatrix`
   hardcoded rows; key `vpnRunning` off `BulwarkVpnService.running`; correct
   `TamperReporter.kt`'s relay claim + the VpnService notification copy; change the
   pinned fail-open dashboard note to "currently UNFILTERED (OCR route planned)". (C4, C5)

**P1 — close the Android loop (the flagship gap)**
4. Wire a `Pipeline` consumer onto `run_android_data_path` (text rules + bundled
   NSFW first-pass via bulwark-infer local, offload-preferred for heavy media). (C2)
5. Wire Android → cluster: `AlertRelay.RaiseAlert` for tamper/content alerts + a
   periodic `Heartbeat` (JNI or Kotlin gRPC). (C3)
6. Persist the Android per-install CA (Keystore-backed `CaKeyStore`). (Med)
7. Device-identity (mTLS subject) binding for Heartbeat/Get/Stream — natural
   follow-on of P0-1's client-cert PKI. (Med×2)

**P2 — promised functionality**
8. Host/SNI blocklist + HTML/text response gating (make "block adult pages" true,
   or downgrade PLAN §0a to alert-only honestly).
9. Android review-decision wiring (approve → allowlist), QR scan on child, NFC,
   `require_always_on` → `Lockdown.enforce`, enforcement-tier badge.
10. Doc corrections from §5 (one sweep).

**P3 — known roadmap** (already tracked): OCR agent capture, supervision OAuth,
desktop transparent pumps, gossip/Postgres, WebRTC, SMS/calls.
